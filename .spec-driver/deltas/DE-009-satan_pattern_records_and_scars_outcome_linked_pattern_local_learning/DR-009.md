# DR-009 – SATAN pattern records and scars - outcome-linked pattern-local learning

## 1. Executive Summary

- **Delta**: [DE-009](./DE-009.md)
- **Status**: draft (update when approved)
- **Last Updated**: 2026-06-03
- **Synopsis**: Build the missing *pattern-local* half of SATAN's outcome learning.
  The outcome observer already turns classified interventions into **global**
  attribute deltas; this adds durable **pattern records** whose counters and scars
  are derived — as a rebuildable SQL projection — from those same outcomes, matched
  against an immutable snapshot of the percept handles present when each intervention
  fired. No change to the global-attribute path.

## 2. Problem & Constraints

- **Current Behaviour**: `dl-satan-observer` classifies matured interventions
  (worked/ignored/neutral/contradicted/harmful) → `satan_intervention_outcomes`
  projection + an enqueue that drives **global** attribute deltas via
  `dl-satan-attribute-listener`. Nothing accrues against the recurring *cue-shape*
  the intervention acted on. The `patterns_attributes` design note mandates that each
  outcome update **both** global attributes **and** the implicated pattern record;
  only the global half exists.
- **Drivers / Inputs**: vision §3/§7; `patterns_attributes.design_note.md`;
  `epistemics-roadmap.md` (step 1 of patterns→probe→hypothesis).
- **Constraints / Guardrails**:
  - No regression to the global-attribute outcome path — enforced structurally
    (§3.2), not merely asserted.
  - Projection doctrine: the audit transcript is the source of truth; DB tables are
    projections rebuildable by replay. **Attribution inputs must be audited** — hence
    the percept-handle snapshot is written into the `intervention.created` audit
    event, not read from the mutable `percept.json` side-artifact.
  - POL-001: pattern store is pure DB logic — incidental elisp tenant. Co-locate v1.
- **Out of Scope**: action-gate enforcement of `intrusion_ceiling`/`cooldown_until`;
  `cooldown_until` derivation; `last_seen_at`; auto-mining patterns; probe surface;
  hypothesis board; habitat rendering; the live read/match path into the percept loop.

## 3. Architecture Intent

- **Target Outcomes**:
  - Durable pattern definitions keyed by a conjunctive `cue_handles` shape.
  - Each intervention carries an **immutable, audited snapshot** of its run's percept
    handles (`satan_interventions.percept_handles_json`).
  - A rebuildable projection attributing each mature outcome to every pattern whose
    cue-shape is contained in that intervention's snapshot.
  - Counters + scars derivable from that projection; scars reference the outcome.
- **Guiding Principles**: derive, don't push; audited inputs only; precise attribution
  over dense; strict-first, loosen-with-evidence; the new subsystem cannot endanger
  the existing global path.

### 3.1 Data flow

The match is a JSONB containment join — no file reads, no elisp loop, deterministic:

```
intervention.created  ──stamps──▶ satan_interventions.percept_handles_json
   (snapshot of run percept :handles; [] for interventions with no percept)

satan-pattern-rebuild (one tx, advisory lock):
  TRUNCATE satan_pattern_outcomes
  INSERT … SELECT
    FROM satan_patterns p
    JOIN satan_interventions i
         ON i.percept_handles_json @> p.cue_handles_json      -- p.handles ⊆ i.snapshot
    JOIN satan_intervention_outcomes o ON o.intervention_id = i.id
    WHERE o.maturity = 'mature' AND o.classification <> 'unknown'
        ▼
  satan_pattern_outcomes(pattern_id, intervention_id, classification, ts=i.ts)
        ▼
  VIEW satan_pattern_stats  (counts, last_tested_at, last_outcome)
  scars = satan_pattern_outcomes WHERE classification IN ('contradicted','harmful')

broker classify path / global-attribute path: UNCHANGED
```

### 3.2 Non-regression is structural, not asserted

Three guarantees protect the global path:
1. **Live path** — `intervention-create` only *adds* a `percept_handles_json` column
   write to the existing INSERT/audit payload; the global-attribute enqueue is untouched.
2. **Observer** — the `satan-pattern-rebuild` call runs **last**, after classification
   and the global enqueue have committed, wrapped in a guard that catches every error
   (including `require`/migration-availability failures of the pattern module) and logs
   without signalling. A broken pattern subsystem degrades to stale pattern stats; it
   cannot abort the tick or block classification.
3. **Isolation** — the pattern module is `require`d behind the same guard, so a
   load-time error never propagates into the observer's classification path.
   `VT-rebuild-guard` injects a simulated failure to prove all three.

### 4.1 Schema (0007_patterns.sql)

```sql
-- audited attribution input: snapshot of the run's percept handles at fire time.
-- Existing rows backfill to '[]' (predate the feature → match nothing; acceptable).
ALTER TABLE satan_interventions
  ADD COLUMN percept_handles_json JSONB NOT NULL DEFAULT '[]'::jsonb;
CREATE INDEX satan_interventions_percept_handles_gin
  ON satan_interventions USING GIN (percept_handles_json jsonb_path_ops);

-- definitions; satan-pattern-sync is sole writer
CREATE TABLE satan_patterns (
  id                    TEXT PRIMARY KEY,
  label                 TEXT NOT NULL,
  cue_handles_json      JSONB NOT NULL,            -- conjunctive cue-shape
  default_intervention  TEXT,
  intrusion_ceiling     TEXT,                      -- recorded, NOT enforced in v1 (R2)
  priority              INTEGER NOT NULL DEFAULT 0,
  enabled               BOOLEAN NOT NULL DEFAULT true,
  notes                 TEXT,
  updated_at            TIMESTAMPTZ NOT NULL
);

-- projection: truncate + rebuild from mature, non-unknown outcomes.
-- NO FK to satan_interventions: 0006's rebuild does
-- `TRUNCATE satan_intervention_outcomes, satan_interventions` and PostgreSQL
-- refuses to truncate a table an un-listed FK child references. intervention_id
-- is a plain indexed column; the rebuild only ever inserts live ids, so it
-- cannot dangle in practice.
CREATE TABLE satan_pattern_outcomes (
  pattern_id      TEXT NOT NULL REFERENCES satan_patterns(id) ON DELETE CASCADE,
  intervention_id TEXT NOT NULL,
  classification  TEXT NOT NULL CHECK (classification IN
                    ('worked','neutral','ignored','contradicted','harmful')),
  ts              TIMESTAMPTZ NOT NULL,            -- intervention firing time
  PRIMARY KEY (pattern_id, intervention_id)
);
CREATE INDEX satan_pattern_outcomes_intervention_idx
  ON satan_pattern_outcomes(intervention_id);

CREATE VIEW satan_pattern_stats AS
SELECT
  p.id AS pattern_id,
  count(*) FILTER (WHERE o.classification = 'worked')       AS success_count,
  count(*) FILTER (WHERE o.classification = 'ignored')      AS ignored_count,
  count(*) FILTER (WHERE o.classification = 'contradicted') AS contradicted_count,
  count(*) FILTER (WHERE o.classification = 'harmful')      AS harmful_count,
  max(o.ts)                                                 AS last_tested_at,
  (SELECT o2.classification FROM satan_pattern_outcomes o2
     WHERE o2.pattern_id = p.id
     ORDER BY o2.ts DESC, o2.intervention_id DESC LIMIT 1)  AS last_outcome
FROM satan_patterns p
LEFT JOIN satan_pattern_outcomes o ON o.pattern_id = p.id
GROUP BY p.id;
```

`unknown`/pending and immature outcomes are excluded at the rebuild `WHERE`, so the
view never treats a pending row as "tested" (Codex MAJOR). The `last_outcome`
tie-breaker (`ts DESC, intervention_id DESC`) is deterministic across interventions
sharing a run's frozen `time_now` (Codex MAJOR).

Scars are not a table: `… WHERE classification IN ('contradicted','harmful')`. A scar's
narrative is `outcome.evidence_json` (written atomically with the outcome row, always
present); the counter-memory trace (which inherits the *intervention's* cue handles)
is a best-effort enrichment that may be absent if its write failed — so scars never
depend on it (Codex BLOCKER, dangling pointer).

### 4.2 `patterns.eld` shape

```elisp
;; satan/patterns.eld — curated SATAN pattern definitions
((:id "docs-after-error"
  :label "Docs browsing after a config error"
  :cue_handles ("transition:error->browser" "domain_kind:docs" "artifact:none")
  :default_intervention "ask_extract"
  :intrusion_ceiling "inbox"
  :priority 5
  :enabled t
  :notes "...")
 ...)
```

`satan-pattern-sync`:
- validates each `cue_handle` against the canon grammar (`dl-satan-memory-grammar`),
  **rejecting unknown handles** (a typo'd handle would silently never match — Codex F3);
- upserts definition columns (idempotent);
- sets `enabled = false` for any DB row absent from the file (soft retire, never deletes).
  `enabled` gates only *future live action* (the out-of-scope gate); it does **not**
  gate historical attribution, so a retired pattern keeps its scars.

**Definition mutability:** rebuild rematches *all* outcomes against *current*
definitions, so editing a pattern's `cue_handles` retroactively re-attributes its
history (consistent with "projection over current beliefs"). Convention: a meaningful
cue change should use a **new `pattern_id`** rather than mutating an existing one, to
preserve historical blame (Codex MAJOR).

### 4.3 Matching

`pattern ⊆ percept-snapshot` is expressed directly as the JSONB containment operator
`i.percept_handles_json @> p.cue_handles_json` in the rebuild SELECT — no elisp set
loop, GIN-indexed. (A small pure `dl-satan-pattern-match` helper is deferred to the
live read path along with `last_seen_at`.)

### 4.4 Snapshot + rebuild

- **Snapshot.** `dl-satan-intervention-create` reads `:percept-handles` from the
  tool-ctx (threaded from `run_ctx`'s `:percept`), and stamps it as
  `percept_handles_json` on both the `intervention.created` audit payload (extending
  the audit validator) and the projection INSERT. Interactive/MCP runs with no percept
  yield `[]` (honest — they match nothing; see IMPR-010).
- **Rebuild.** `satan-pattern-rebuild` runs `TRUNCATE satan_pattern_outcomes` + the
  containment `INSERT … SELECT` (§3.1) inside **one transaction** guarded by
  `pg_advisory_xact_lock(<rebuild key>)` — readers see the prior rows until COMMIT (no
  empty-table window) and overlapping observer/manual rebuilds serialize (Codex
  BLOCKER). Head-only: it reads the current `satan_intervention_outcomes` head verdict,
  so an outcome later revised away from harmful/contradicted simply stops being a scar
  on the next rebuild (stated policy — Codex MAJOR). Invoked **last** in the observer
  tick, fully guarded (§3.2).

## 7. Design Decisions & Trade-offs

- **DEC-1 — Projection/rebuild over live listener.** Doctrine already makes projections
  rebuildable from the audit log; deriving = zero broker-classify coupling, simplest.
  *Trade-off:* stats lag by one tick. Fine for slow-moving patterns.
- **DEC-2 — Scar = structured edge; narrative in `outcome.evidence_json`.** Avoids
  §15 memory-mush (no prose duplication) *and* the dangling-pointer hazard: evidence_json
  is written with the outcome row, so a scar is always readable even if the counter-memory
  write failed. Counter-memory (tagged with intervention handles) is best-effort enrichment.
- **DEC-3 — Definitions in `patterns.eld`, grammar-validated sync.** Few, hand-authored,
  reviewable; no runtime sprawl (R1). `enabled` gates action, not attribution.
  *Trade-off:* no agent-driven creation in v1.
- **DEC-4 — Containment-subset over an immutable percept snapshot.** *Why subset not
  overlap:* mechanical-shame integrity demands correct attribution; overlap
  cross-contaminates (§15 crank suspicion). *Why a snapshot, not `percept.json`:* the
  attribution input must be audited and immutable for the projection to be truly
  rebuildable — reading the mutable `percept.json` would make history depend on
  filesystem state (Codex). Snapshotting the percept handles onto the
  `intervention.created` event makes the match pure, deterministic SQL and grounds blame
  in "the cue surface present when *this* intervention fired." *Accepted consequence:*
  attribution is sparse (interventions whose percept lacks a pattern's full shape match
  nothing; those outcomes still drive global attributes). *Strict-first:* defer any
  threshold/partial match until production shows sparsity is a problem.
- **DEC-5 — definitions table + outcome projection + stats view.** Disjoint writers
  (sync vs rebuild); projection truncatable without risking definitions. *Deferred:*
  `cooldown_until` (enforcement-side, R2) and `last_seen_at` (needs percept scan / the
  read path).
- **DEC-6 — Full SQL rebuild at tick: one tx + advisory lock, mature/non-unknown only,
  head-only, guarded+isolated.** Mirrors 0006's tx-wrapped rebuild; the advisory lock
  serializes overlap; the guard/isolation makes non-regression structural (§3.2).
  *Trade-off:* `O(outcomes × patterns)` containment join per tick — set-based in the DB
  with a GIN index; revisit incremental rebuild only if volume warrants (open question).

## 9. Rollout & Operational Notes

- **Migration**: forward-only `0007_patterns.sql`; `ALTER … ADD COLUMN … DEFAULT '[]'`
  backfills existing interventions harmlessly. Empty `patterns.eld` is a valid cold
  start. `satan-pattern-rebuild` is idempotent + advisory-locked.
- **Nix**: `dl-satan-pattern.el` is a new `.el` — `git add` for the flake parser, then
  `home-manager switch`. `patterns.eld` is data (`read`), not a `use-package` form. Run
  `bin/elisp-locate-paren-error` after every `.el` edit.
- **Recovery / Rollback**: remove the observer's rebuild call to disable; the snapshot
  column and projection tables are inert with no effect on the global-attribute path.
