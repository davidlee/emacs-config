# DR-002 – satan-attrd integration tests leak test:<uuid> rows into production satan_memory

## 1. Executive Summary

- **Delta**: [DE-002](./DE-002.md)
- **Status**: draft (update when approved)
- **Repo**: code in `~/dev/satan-attrd/` (separate git repo); artefacts here in `~/.emacs.d/`.
- **Last Updated**: 2026-05-30
- **Synopsis**: Integration tests stop sharing a long-lived database. Each test
  binary self-provisions a throwaway `satan_attrd_test_<bin>_<uuid>` database from
  an admin connection derived from `DATABASE_URL`, migrates+seeds it, and runs
  against it. Production `satan_memory` ceases to be a write target by
  construction; per-test `cleanup_*` bookkeeping is deleted because a disposable
  database makes panic-leaks impossible.

## 2. Problem & Constraints

- **Current Behaviour**: Tests connect to `$DATABASE_URL` (`common::shared_pool`).
  In the dev shell `.envrc` sets that to `postgres:///satan_memory?host=/run/postgresql`
  — **production**. Per-test isolation is `unique_scope()`/`unique_run_id()` plus a
  **best-effort inline `cleanup_*` call at each test tail**. Any panic/assert-fail
  before that line orphans rows. Observed 2026-05-30: 3 leaked `test:<uuid>` scopes
  / 12 rows from one failed run, polluting drift/observability reads of
  `satan_attributes`.
- **Two distinct defects** (the issue named only the second):
  1. **Targeting** — bare `cargo test` can write production at all (env/config).
  2. **Panic-leak** — even in the correct DB, a failing test orphans rows (isolation).
- **Drivers / Inputs**: ISSUE-003. Three conflicting `DATABASE_URL` notions found:
  `.envrc` → `satan_memory` (prod); `Justfile` → `…@127.0.0.1:54322/postgres`
  (supabase-local); `HANDOVER.md` → `satan_memory_test` (intended). The active
  `.envrc` prod URL is how the leak reached production.
- **Constraints / Guardrails**:
  - clippy `-D clippy::unwrap_used -D clippy::expect_used` is non-negotiable
    (satan-attrd `AGENTS.md`); test code already `#![allow(...)]`s these in
    `common`, but new harness code outside that allow must comply.
  - `just check` (lint + format + test) must stay green.
  - No auto-migrate on daemon start (unchanged; migration stays an explicit step).
  - Cross-repo: code commits land in `satan-attrd`; never write `~/.emacs.d/` from
    that repo's commit.
- **Out of Scope**:
  - Immediate remediation flush of existing orphans
    (`DELETE FROM satan_attributes WHERE scope LIKE 'test:%'`) — destructive prod
    write, human-run, tracked on ISSUE-003.
  - Broker (elisp) changes; attribute semantics / design-contract changes.

## 3. Architecture Intent

- **Target Outcomes**:
  - Integration tests can **never** write production `satan_memory` — the harness
    only ever connects to the maintenance db `postgres` (to administer) and to its
    own generated `satan_attrd_test_*` database (to test).
  - A panicking/failing test **leaves no orphaned rows** — its entire database is
    disposable and reclaimed.
  - The `DATABASE_URL` discrepancy collapses to one meaning: a **server pointer**;
    its database component is ignored by tests.
- **Guiding Principles**:
  - Isolation by **disposal**, not by bookkeeping. Cheapest correct end state:
    delete the cleanup apparatus rather than make it panic-safe.
  - Safety **by construction** over safety by discipline: prod is unreachable
    because the harness never targets its name, not because callers remember an
    env override.
- **Lifecycle Impact**: test databases are ephemeral; created at binary start,
  reclaimed at the next run's start sweep.

### 4.1 Harness design

```rust
// with_db: keep host/socket/creds/params of `url`, replace the database name.
// Handles both `postgres:///NAME?host=/run/postgresql` (socket) and
// `postgresql://user:pw@host:port/NAME` (tcp). Prefer mutating sqlx's
// PgConnectOptions (.database(name)) over string surgery — robust to the
// socket `?host=` form which is awkward to edit textually.
fn with_db(url: &str, db: &str) -> String { /* parse PgConnectOptions, .database(db) */ }

const SWEEP_LOCK_KEY: i64 = 0x5A7A_4474; // arbitrary fixed advisory-lock key

pub async fn shared_pool() -> PgPool {
    init_log();
    let base = std::env::var("DATABASE_URL")
        .expect("DATABASE_URL must be set (server pointer; its db component is ignored)");

    // One dedicated admin *connection* (not a pool) so the session advisory
    // lock is held on a known connection for the whole sweep+create+connect.
    let mut admin = PgConnection::connect(&with_db(&base, "postgres")).await.unwrap();

    // Serialise sweep+create across concurrently-starting test binaries. Without
    // this, binary B's sweep could DROP binary A's freshly-CREATEd DB during the
    // window before A connects its pool (the DB has no live connections yet).
    sqlx::query("SELECT pg_advisory_lock($1)").bind(SWEEP_LOCK_KEY).execute(&mut admin).await.unwrap();

    sweep_stale(&mut admin).await;          // §4.2 — GC dead test DBs

    let name = format!("satan_attrd_test_{}_{}", BIN_TAG, Uuid::new_v4().simple());
    assert!(name.starts_with("satan_attrd_test_"));        // belt: never prod
    sqlx::query(&format!(r#"CREATE DATABASE "{name}""#)).execute(&mut admin).await.unwrap();

    // Connect the test pool *before* releasing the lock, so the new DB has a live
    // connection and is therefore skip-protected against any sibling's sweep.
    let pool = PgPoolOptions::new().max_connections(2)
        .connect(&with_db(&base, &name)).await.unwrap();

    sqlx::query("SELECT pg_advisory_unlock($1)").bind(SWEEP_LOCK_KEY).execute(&mut admin).await.unwrap();

    migrate::run_migrations(&pool).await.unwrap();          // seeds 8 globals + settings
    pool
}
```

- **Advisory lock closes the create/sweep race** (DEC-4): the lock is held on a
  single `PgConnection` across sweep → create → first pool connect → release.
  By release time the new DB has a live connection, so a sibling that next acquires
  the lock and sweeps sees it as in-use and skips it.
- `BIN_TAG`: a per-integration-binary discriminator so the four binaries
  (`store`/`decay`/`dispatcher`/`run_loop`) get distinct DB-name prefixes for
  readability. `module_path!()`/`env!("CARGO_CRATE_NAME")` do **not** distinguish
  integration binaries; the chosen mechanism is a `const BIN_TAG: &str = "…";`
  declared in each test file and passed in (small, explicit). Final form picked at
  implementation; correctness does not depend on it (uuid already guarantees
  uniqueness) — purely a debugging affordance.

### 4.2 Teardown / GC

Rust integration tests have **no cross-binary global teardown** (each test file is
its own binary; libtest offers no after-all hook). End-of-run drop is therefore
unreliable. The reclaimer is **sweep-on-init**:

```rust
// Caller holds SWEEP_LOCK_KEY advisory lock on `admin` (see shared_pool).
async fn sweep_stale(admin: &mut PgConnection) {
    let dbs: Vec<String> = sqlx::query_scalar(
        "SELECT datname FROM pg_database WHERE datname LIKE 'satan_attrd_test_%'")
        .fetch_all(&mut *admin).await.unwrap();
    for db in dbs {
        // DROP DATABASE errors with 55006 (object_in_use) if it has live
        // connections — so DBs of concurrently-running sibling binaries are
        // skipped naturally. Dead DBs from prior runs are reclaimed.
        let _ = sqlx::query(&format!(r#"DROP DATABASE IF EXISTS "{db}""#))
            .execute(&mut *admin).await;   // ignore in-use errors
    }
}
```

- **Two layers stop a cross-kill**: (1) the advisory lock serialises sweep+create
  so a sibling's DB always has a live pool connection by the time another binary
  sweeps; (2) even absent the lock, `DROP DATABASE` fails on a DB with live
  connections (55006) and the error is ignored. Steady state ≈ 4 live test DBs
  (one per binary in the current run). Self-healing across runs.
- **No `WITH FORCE`**: force-terminating connections could nuke a live sibling on
  any name overlap; the in-use skip is the safer invariant. (DEC-4.)
- No shell trap / `just` post-step needed; an optional one would be redundant.

## 5. Verification Alignment

| Verification | Impact | Notes |
| --- | --- | --- |
| VT-no-prod | new | **Headline proof.** Assert `SELECT current_database()` on the live pool matches `satan_attrd_test_%` and `!= 'satan_memory'`. This is what actually kills the issue: production is never a write target, so no test (panicking or not) can orphan prod rows. |
| VT-sweep-gc | new | Pre-seed a stray `satan_attrd_test_orphan_<uuid>` DB (no live connection), then run a `shared_pool()` and assert the sweep reclaimed it. Proves GC of prior-run leftovers. |
| existing suites | regression | all integration tests keep passing with `cleanup_*` tails removed; `unique_scope`/decay lock retained for intra-binary parallelism. |
| gate | manual | `just check` green; post-run `SELECT … FROM satan_attributes WHERE scope LIKE 'test:%'` on prod returns 0 new rows. |

> Note on panic-safety: with disposable per-binary DBs, "a panicking test leaves no
> orphan" is *trivially* true and not worth a dedicated test — the proof reduces to
> VT-no-prod (prod untouched) plus VT-sweep-gc (any leftover DB is reclaimed next
> run). The earlier framing of a panic-then-assert test was theater and is dropped.

## 6. Supporting Context

- Migrations seed all global state a fresh DB needs: `0007_attributes.sql` seeds 8
  globals at `scope='global'`; `0012_attribute_settings.sql` seeds
  `attribute_updates_enabled`. Decay `tick_*` snapshot/restore works on a freshly
  migrated DB. No out-of-band seeding exists.
- `satan-attrd/AGENTS.md` test rule: integration tests need Postgres on
  `$DATABASE_URL`; unit tests stay pure. This DR keeps that contract — only the
  *meaning* of `$DATABASE_URL` (server vs database) is clarified.

## 7. Design Decisions & Trade-offs

- **DEC-1 — Strategy C (disposable DB)** over A (tx-rollback) / B (RAII guard).
  A needs threading an `Executor`/`&mut PgConnection` through `src/` code-under-test
  and fights the decay `tick_*` writer that hardcodes `Scope::Global` on a `&PgPool`;
  B is a band-aid that still writes whatever DB the env names and wrestles
  `Drop`-can't-`await`. C has the heaviest setup but the **simplest end state**:
  panic-leaks become impossible and the cleanup apparatus is deleted, not hardened.
- **DEC-2 — Per-binary self-provisioning** in the harness, not Justfile
  orchestration. Makes bare `cargo test` safe (no reliance on entering via `just`);
  accepts 4 migrate+seed cycles per run (idempotent, cheap).
- **DEC-3 — Admin URL derived from `DATABASE_URL`** (db→`postgres`), no new env var.
  Reuses existing config; `satan_memory` is never a connection target for writes.
- **DEC-4 — GC by sweep-on-init**, serialised with siblings via a session
  advisory lock held across sweep+create+first-connect, and backstopped by
  `DROP DATABASE` failing on live connections. No `WITH FORCE`.

## 8. Open Questions

- (none blocking) `BIN_TAG` discriminator mechanism — cosmetic; resolved in IP-002.

## 9. Rollout & Operational Notes

- **Migration / Backfill**: none — test-only change; no production schema touched.
- **Observability**: prod `satan_attributes` should stop accruing `test:%` scopes.
- **Recovery / Rollback**: revert the harness change; tests fall back to the prior
  (leaky) behaviour. Low blast radius — no production code path altered.
- **Permissions**: the admin connection needs `CREATEDB`. The local socket role and
  supabase `postgres` role both have it; CI roles must too (note for IP-002).
